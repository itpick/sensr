# Smart host labels — design

Status: draft for owner approval, 2026-11-23.

## Why

The dashboard Hosts card lists 70 devices on the live router. 56 have no
name, so the MAC address is the only clue. The owner wants a "smart label"
under the MAC: who made the device and what kind of thing it is. Then a way
to correct the wrong guesses.

## Goals

- Under each MAC on the Hosts card, show **maker · type**. For example
  `Wyze Labs · Camera`, `Raspberry Pi · Computer`, `HP · Printer`, or
  `Private MAC · Phone/laptop`.
- Every label carries a confidence (high / medium / low). A low-confidence
  label is styled as a guess ("probably a camera"), never as a fact.
- A tooltip says *why*: the evidence used. For example "MAC maker:
  Wyze Labs; mDNS: _wyze._tcp".
- Part B: the owner can override the type and the maker per device. The
  override always wins, and it is labelled "set by you".
- The labels are also exposed in the hosts API view, so later features can
  use them: per-host analysis, allowlist presets and notifications.

## Non-goals

- No active scanning: no nmap, port probes or TCP/OS fingerprinting.
- No cloud lookups (for example the Fingerbank API). No device data ever
  leaves the router.
- No renaming hosts. Names stay in DHCP reservations ("Make static").
- No per-type firewall policy yet.

## Anti-goals

- A confident wrong label, for example calling a laptop a camera with
  "high" confidence.
- Extra network chatter, or anything that could disturb a device.
- A large runtime dependency, or a data file under a restrictive licence.
  Wireshark's `manuf` is GPL and Fingerbank's DB is restricted, so neither
  is used.

## Approaches considered

1. Maker only, from the IEEE OUI registry. Cheap, but often vague
   ("Espressif").
2. **Maker + type (chosen).** OUI, plus evidence the router can already see
   passively: DHCP hostname, DHCP vendor class (option 60), DHCP parameter
   list (option 55) and mDNS announcements. Combined by our own rule table,
   with a confidence on every label.
3. Option 2 plus owner overrides. **Also chosen, as part B**, built after
   option 2.

The owner picked "maker + type, then overrides".

## Design

### New crate `sensr-fingerprint` (pure, no I/O)

**`oui::lookup(mac) -> Option<&'static str>`**
- A short maker name from an embedded table.
- The table covers the IEEE MA-L, MA-M and MA-S registries, matched
  longest prefix first.

**Table**
- Committed as `crates/sensr-fingerprint/data/oui.tsv` (`prefix<TAB>name`,
  sorted).
- Generated by `cargo xtask oui`, which downloads the three IEEE CSVs from
  standards-oui.ieee.org.
- Names are shortened by stripping legal suffixes ("Co., Ltd.", "Inc.",
  "Corporation", "GmbH" and so on).
- A small alias map fixes well-known names, for example:
  - "Raspberry Pi Trading Ltd" → "Raspberry Pi"
  - "Hon Hai Precision…" → "Foxconn"
- IEEE registry data is public.
- A monthly GitHub workflow runs `xtask oui` and opens a PR when the table
  changes. This follows the "latest of everything" directive.

**`private_mac(mac) -> bool`**
- True when the locally administered bit is set.

**`classify(&Evidence) -> Label`**

```text
Evidence { mac, hostname, dhcp_vendor_class, dhcp_prl, mdns_services, mdns_model }
Label    { maker: Option<String>, kind: Kind, confidence: Confidence, reasons: Vec<String> }
Kind     = Phone | Tablet | Computer | Tv | Speaker | Camera | Printer | Console
         | Network | SmartHome | Server | Wearable | Unknown
Confidence = High | Medium | Low
```

**Rule table**
- An ordered Rust table of our own. The first match per signal wins, then
  signals are combined.
- **High** — explicit device statements:
  - mDNS model TXT: Apple `model=`, Google Cast `md=`
  - mDNS service types: `_ipp`/`_printer` → Printer; `_googlecast` → Tv;
    `_airplay` with a speaker model → Speaker; `_hap` → SmartHome
  - DHCP vendor class: `android-dhcp-*` → Phone; `MSFT 5.0` → Computer
- **Medium:**
  - Single-purpose makers: Wyze, Ring and Reolink → Camera; Sonos → Speaker;
    Roku → Tv; Nintendo → Console; Ubiquiti → Network
  - Hostname patterns: `iPhone`, `Galaxy-`, `DESKTOP-XXXX`, `HP[0-9A-F]{6}`
    (HP printers)
  - DHCP option-55 fingerprints for iOS, macOS, Windows and Linux
- **Low:** a generic maker alone, for example Espressif → SmartHome or
  Raspberry Pi → Computer.

**Private MAC**
- When the bit is set, maker is "Private MAC" and the kind comes from the
  other evidence.
- With no other evidence, the label reads "Private MAC · Phone/laptop?" at
  Low. Phones, tablets and laptops are what randomise.
- Container and VM prefixes (`02:42`, `52:54:00`) are recognised as "Virtual
  machine/container".

Every rule has a unit test using real-world evidence strings.

### Evidence capture (sensr-agent)

**Sniffer thread `sensr-fp`**
- One passive AF_PACKET socket per internal interface. This reuses the
  socket2/nix pattern from `arp_intercept.rs` and is Linux-gated.
- A classic BPF filter keeps only `udp dst port 67`, plus `udp port 5353`
  on IPv4 and IPv6. It never transmits on this socket.
- Parses:
  - DHCP DISCOVER/REQUEST: chaddr, option 12, option 60 and option 55.
  - mDNS responses and announcements: PTR service types, TXT `model=` /
    `md=`, and the source MAC.
- Malformed packets are dropped silently. The parsers are fuzz-friendly
  pure functions in `sensr-fingerprint`.

**One gentle mDNS query**
- A single DNS-SD query, `_services._dns-sd._udp.local PTR`, from the
  router on each internal interface at start, then every 15 minutes.
  - This elicits answers from devices that only respond to queries.
  - Rate: one packet per interface per 15 minutes.

**Storage**
- Evidence is stored on the host row in `hosts.json` as an optional
  `evidence` object.
- Its lists are capped: at most 16 service types, and the PRL as a string.
- The evidence only changes the row's "structure" when it changes, so
  flushes stay rare.

**Settings**
- `hosts.fingerprint.enabled` (default true) turns off the sniffer and the
  query.

### API and UI

**API**
- The hosts view gains `label: {maker, kind, confidence, reasons[], by:
  "auto"|"owner"}`.
- `label` is computed at view time, not persisted, so rule improvements
  apply on upgrade.

**Hosts card**
- A second, muted line sits under the MAC cell, with a small type icon and
  `maker · type`.
- Low confidence is shown in italics with a trailing "?".
- The `title` tooltip lists the reasons. No new column.

### Part B: owner overrides

**Config**
- `hosts.labels: ArrayField<HostLabel { enabled, mac, kind: Option<Kind>,
  maker: Option<String>, description }>`.
- A set field wins over the automatic one. An unset field falls back to
  auto.

**Operation**
- `Op::HostLabelSet { mac, kind, maker }` uses the same atomic-commit
  pattern as `Op::HostModeSet`.
  - It commits directly when the candidate equals head and no confirm is
    pending. Otherwise it stages.
  - Commit message: `set host label <mac> → <kind>/<maker>`.
  - Clearing both fields removes the entry.
- REST: `POST /api/v1/hosts/label`.

**UI**
- A small pencil next to the label opens an inline editor: a type select
  (the Kind list plus "Auto") and a maker text box (blank = auto).
- The editor has Save and Reset-to-auto.
- An owner label shows "set by you" in the tooltip.

## Constraints

- Rust toolchain and latest dependencies, per the repo rules. No new heavy
  deps: DHCP and mDNS parsing are hand-rolled over byte slices.
- The sniffer runs only on internal interfaces and never on WAN.
- No AI attribution in commits or PRs.
- Playwright e2e covers the label line and the override editor, using the
  existing hosts fixture.

## Left to the builder

- Exact icon glyphs, and the alias-map contents beyond the examples.
- The exact option-55 fingerprint strings, taken from well-known public
  observations and written as our own rules.
- How evidence merges when a host appears under both a client-id row and a
  MAC row. The MAC row wins, matching the inventory's absorb logic.
